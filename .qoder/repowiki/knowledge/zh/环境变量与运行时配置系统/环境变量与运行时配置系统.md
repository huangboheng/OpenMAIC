本仓库采用 Next.js App Router，配置系统完全基于 Node.js 原生 `process.env` 和 Next.js 的 `NEXT_PUBLIC_` 前缀机制，没有独立的配置文件（如 .env、config.yaml、application.properties）或专门的配置管理库。所有配置以环境变量形式直接在各模块中读取。

**加载方式与环境变量分类**
- **服务端配置**：在 API Route 中直接使用 `process.env.XXX` 读取，如 `ACCESS_CODE`、`TRUST_PROXY_HEADERS`、`NODE_ENV`、`npm_package_version` 等，用于访问控制、代理设置、版本信息等。
- **客户端可见配置**：使用 `NEXT_PUBLIC_` 前缀的环境变量，如 `NEXT_PUBLIC_ENABLE_PPTX_IMPORT`，这些会被 Next.js 编译时注入到浏览器端。
- **评估脚本配置**：在 `eval/` 目录下通过 `EVAL_SCENARIO`、`EVAL_AGENT_MODEL`、`EVAL_JUDGE_MODEL`、`EVAL_SAMPLES`、`EVAL_PASS_THRESHOLD`、`DEFAULT_MODEL` 等环境变量控制评测行为。

**架构与约定**
- 无集中式配置中心，每个模块按需直接读取所需环境变量。
- 布尔型开关统一使用字符串比较 `=== 'true'` 判断。
- 生产环境判断依赖 `process.env.NODE_ENV === 'production'`。
- 未定义环境变量时使用默认值（如版本号回退到 `'0.1.0'`）。

**开发者应遵循的规则**
- 新增配置项应优先使用 `process.env` 读取，避免硬编码。
- 需要暴露给浏览器的配置必须加 `NEXT_PUBLIC_` 前缀。
- 敏感信息（如密钥、令牌）不应出现在代码中，应通过部署平台注入环境变量。
- 建议在 `.env.example` 中列出所有必需的环境变量及说明，便于团队协作。
- 对布尔开关统一使用 `=== 'true'` 模式，保持语义一致。

该方案简单直接，适合中小型项目，但缺乏类型校验、默认值管理和集中式文档，随着配置项增多建议引入 zod 或类似库进行运行时验证。
